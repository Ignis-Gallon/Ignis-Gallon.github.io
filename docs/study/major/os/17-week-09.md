# 9주차: 동기화의 하드웨어 지원, TestAndSet

- Bakery Algorithm의 가장 큰 문제점은, 알고리즘이라는 것이다. S/W 만드는 사람이 봤을 때는 잘 동작한다고 볼 수 있지만, 한 번 해결될 때마다 운영체제 내에서 끊임없이 동작해야만 한다.

    - 많은 Loop가 하나의 값을 선택하는 과정이고, 보호받지 못하는 과정인데, 돌아가는 과정에서 어긋나고 섞이는 과정이 발생할 수도 있다. 지극히 S/W적인 관점. 뭐 하나 Application 만들 때 알고리즘은 아무리 복잡해도 상관없지만, 이건 운영체제에서 돌아가고 프로세스에 대하여 매 순간 일어나야 되기 때문에 다소 복잡하다. 그리고, while loop가 밖에 있기 때문에 문제가 생길 수 있다.
    - 어느 순간에 엉킨다고 얘기하기는 힘들지만, 실제 구현의 관점에서 보면 번호표 받는 곳에서 “데드락”에 빠질 수 있다.
    - 그러므로 H/W적인 지원을 해야 한다. 그 역할을 하는 반도체를 만들어서, chip을 사용한다. 특수한 용도로 처리되는 chip 처리. CPU가 갖고 있는 명령어 중에 특정 부분이라도 지원할 수 있는 것이 있다면 좋겠다는 관점에서 시작하는게 Synchronization H/W이다.
    - 마치 MOV, ADD처럼 하나의 명령으로 처리하도록 해보자는 것. (일련의 과정을) 이런 것들이 여러 개의 일들이긴 한데, 이것들이 atomic하게 돌아가면서 일이 틀어지지 않도록 만들어 보자는 것이다.

- atomic하게 하자는 것은, 인터럽트/선점을 막아버리는 것으로 해결이 될 수도 있다. 하지만 효율이 떨어질 수도 있음.
- 메모리에서 워드를 읽어와서 CPU에서 사용하고 다시 저장하는 과정이 atomic하다고 생각될 수도 있지만, 사실 이 과정도 atomic하지 않을 수 있다. (생기려면 생길 수도 있음. 이런 것들이 나눠지지 않도록 하는 무언가가 필요하고, 이런 것을 H/W지원을 받아서 하자는 것.)
- ex) TestAndSet

```c
boolean TestAndSet(boolean *target) {
	boolean rv = *target;
	*target = true;

	return rv;
}
```

이 함수 내의 동작도 잘라질 수 있을 것이다.

```c
//shared data:
boolean lock = false;

do {
	while (TestAndSet(&lock));
	// critical section
	lock = false;
	// remainder section
}
```

⇒ 이렇게 하면 atomic 처리는 가능하긴 하지만, H/W로 돌려버려서 애초에 뜯어지지조차 않게 만들어 버린다는 것이 주요 내용.

위의 함수에서 return이 된다는 것은 결국 값을 반환한다는 것이고, return 값은 버스를 통해 이동해서 메모리 어딘가에 데이터를 저장한다는 것이다. 즉, 명령 자체는 atomic 하지만, 그 return 값을 받아서 저장한다는 것까지 atomic하지는 않다! 그래서 파고 들면 이런것까지 해결될 수는 없을 수도 있다.

- Mutual Exclusion(Mutex)

만약 이미 누가 Critical Section을 쓰고 있어서 다른 프로세스가 들어가지 못하고 대기하고 있다면, 해당 프로세스들은 다른 일을 하거나 계속해서 기다리는 것이 아니라, TestAndSet()을 계속 수행해 보면서 돌아갈 수 있나 체크하고 있게 된다.

이를 busy waiting, spin lock 라고 한다.

그래서, Mutex를 쓰더라도 이와 같이 busy waiting은 해결하기 힘들더라.

---

CS에 들어가려는 프로세스가 많고 길게 들어갈 수도 있고, CS에 들어가려는 프로세스가 많지 않고 짧게 반복되는 경우도 있다. 하지만, 이 프로세스들은 모두 들어갈려고 계속해서 체크하기 때문에 들어가진 못하면서 생산적인 일을 처리하지 못하기 때문에 busy하게 되고, waiting한다.

⇒ 이를 spin lock이라고 한다. (일반적으로 들어갈 수 있는 권한을 lock이라고 한다.)

이때 프로세스들이 대기하는 장소를 queue라고 한다.

즉, busy waiting으로 인해 performance가 떨어지게 된다. H/W를 만들어도 봤지만 역시 performance가 발생할 수 있게 된다. 그래서 결국 busy waiting을 없애야만 한다.

---

프로세스 동기화에서는 Semaphores(세마포어)가 최종적인 해결책이다. 즉, 프로세스들이 기다리긴 기다리는데 아무것도 하지 않는다는 것이다. 세마포어는 busy waiting을 요구하지 않을 수 있다. 중요점은 무엇이 달라서 기다리지 않는가? 이다.

Semaphore S는 integer variable이다.

두 개의 동작이 있으며, 하나는 wait(S), 하나는 signal(S)이다.

- wait(S)

```c
while S <= 0 do no-op;
	S--;
```

S가 있는데, 만약 S가 0 이하이면 기다리게 한다. 

- signal(S)

```c
S++;
```

S를 증가시킨다.

이 두 연산과 S로 무엇을 한다는 것일까? 권한을 획득하는 과정이다. wait은 정말 기다리는 것이고, 남이 못가져가게 S를 줄여버리는 것이다. signal은 S를 증가시키는 것이다. 그럼 S가 무한대가 될 수 있지 않을까? 아니다. wait이 먼저 동작하기 때문으로 보인다.

- no-operation : ready queue에 있는 프로세스들은 동작을 하지 않는다. 즉, 실제 프로그램이 돌아가지 않는다는 것이다. wait을 예로 들면, while S≤0을 체크하지 않는다는 것이다. 즉, 한 번만 체크하고나면 나중에 불러줄 때까지 기다리고 있으라는 뜻. (waiting queue에서 대기하고 있으면 pick하는 쪽이 가져오게 된다.)

```c
// Shared data
	semaphore mutex; // Initially mutex = 1

do {
	wait(mutex);
		// critical section
	signal(mutex);
		// remainder section
} while (1);
```

- 이전에는 Program Level에서 다음에 들어올 프로세스를 체크했다. 즉, user level. 이번에는 내가 설정해놓고 기다리면 운영체제가 선택하는 kernel level이 된다. 운영체제가 반드시 도와주어야만 한다는 뜻이다.

더 이상 critical section에 들어가지 못하고 기다리게 될 때, 기다리게 만드는 것을 block, suspend라고 한다. (야구에서 투수가 던지기도 전에 타자가 칠수 없듯이, 동작을 하려면 필요한 상황이 만들어지길 기다려야 한다는 뜻)

- block : 상대방에게 데이터가 와야만 동작할 수 있는 것. 계속해서 기다리고 있는 것으로 보인다.
- non-block : 일단 다음에 무언가 도착할 것이라는 걸 알고 있는 상태에서 자기가 할 걸 하다가 돌릴 상태가 되면 돌아와서 돌리게 되는 것…
- no-operation을 하려면 OS의 도움이 필요하다는게 중요.
- wait(S):

```c
S.value--;
if (S.value < 0) {
	add this process to S.L;
	block;
}
```

- signal(S):

결국 가장 큰 차이는 user level, kernel level.

- Deadlock

두 개의 Semaphore가 있는데 하나는 S고 하나는 Q이다. 두 개의 프로세스가 동시에 wait을 하게 되면, (마치 이전의 경우처럼, 순서가 섞여버리면) 

P0 wait(S)

P1 wait(Q)

p0 wait(Q)

p1 wait(S)

이 상황이 발생해버리면 둘 다 lock을 부여받지 못하고 기다리게 됨. dead lock!. 구조를 잘못만들면 이러한 상황이 발생할 수 있다. (운영체제의 잘못이 아니라 구조 자체가 그렇게 짜이면 dead lock이 발생할 수 있다.) 특히 I/O 자원에서 이런 상황이 많이 발생하는 것으로 보인다.

---

- Binary Semaphore : 0 또는 1만 가지게 하는 것
- Counting Semaphore : 음수부터 양수까지 다 쓰는 것. 보통 이걸 더 많이 씀.
- Bounded-Buffer Problem

- Readers-Writers Problem : 메모장 하나를 공유하고 있다. 그런데 그 내용은 한 컴퓨터에만 저장될 수 있다고 할 때, 읽는 것이 문제일까 쓰는 것이 문제일까? ⇒ 문제는 쓰고 읽는 것이다.

    - 메모장을 50명이 동시에 열었다. 안에 여러 글이 써 있다. 모두에게 그게 뜬다. 그런데 나는 동해물과를 바꾸고 싶고 다른 사람은 마르고 닳도록을 바꾸고 싶다. 하지만 나는 마르고 닳도록을 그대로 두고 싶다. 이러면 원치 않는 결과가 발생할 수 있다.
    - 그래서 여기서 바꾸는 것은 단순히 write를 하도록 만들었지만, write를 할 수 있는 조건을 복잡하게 read에 넣어준다.
    - 내가 쓰는 것은, 아무도 쓰고 있지 않을 때 쓸 수 있게 된다. 즉, 하나를 바꾸는 것은 한 번에 한 사람만 할 수 있도록 한다. lock을 하나 탁 치고 간다? 누군가가 들어간다. 그럼 읽을 수는 있는데, 쓰지는 못한다는 것이다. 언제 쓸 수 있느냐? ⇒ 쓰던 프로세스가 나가서 signal(wrt)을 해주게 되면 그 다음 프로세스가 wait(wrt)하다가 lock을 얻고 들어가게 된다. 
    - 누군가가 쓰고자 하면 wait(wrt)를 해서 들어가서 쓰고, 다 쓰면 signal(wrt)를 한다. 누가 쓰고 있을 때 다른 사람이 쓰고자 한다면 wait(wrt)를 해서 기다리게 된다. 하지만 읽는 것은 맘대로 읽어도 된다. 그래서 쓰는걸 막음으로써 문제가 없게 하도록 한다.  

- Dining-Philosophers Problem : 운영체제에서 아주 유명한 문제.

    - 원형 식탁에 철학자의 의자가 5개 있다.
    - 이 분들은 대화를 하며 사색을 한다. 서로 대화하지도 않고, 의자에서 내려오지도 않는다. 때가 되면 누가 알아서 상도 차려준다. 젓가락을 이용해 식사를 하는데, 젓가락이 쌍으로 있는게 아니라, 하나씩만 있다. (즉, 젓가락 낱개로 5개가 있음. 근데 젓가락은 2개를 쌍으로 써야 한다.) 

    - 떠오르는 문제

        - 젓가락이 하나밖에 없으니까 두 개를 갖고 있던 철학자가 내려놓으면 그 중 하나를 가져와서 (내가 가진 하나를 사용해) 식사가 가능. → 내가 하나가 부족하면 옆에 쓰는 철학자가 다 쓰기를 기다리면서 내 꺼 하나를 들고 기다림. 문제는, 다섯 명이 동시에 배가 고파지면 옆을 쳐다보면서 다섯 명이 다 기다린다. (다 한 손에 하나 들고 기다리면서 지켜보고 있음. 그래서 아무 것도 하지 못하고 계속 기다리게 되는 dead lock 상태가 된다.)
        - 정말 프로그램 자체에는 문제가 없지만, (철학하고 먹고 철학하고 먹고…) 각자에게 문제는 없는데 이 자체를 운용하는데 문제가 발생할 수도 있다는 것이다.

    - 이를 해결하는 것이 책에 나온 코드 알고리즘.
