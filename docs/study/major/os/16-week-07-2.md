# 7주차-2: 임계 구역 조건, Peterson's Solution

## 문제점

- Critical Section을 만족하기 위해서는 아래 세 개를 만족해야 함.

    - Mutual Exclusion

        - turn은 반드시 i 또는 j만 가능하기 때문에 Mutual Exclusion은 가능하다.

    - Progress

        - 먼저, 초기값이 i라고 하고, Pi가 먼저 간다고 하면 Pi는 Critical Section에 들어간다. 동시에 Pj는 들어갈 수 없고, Pi의 exit section이 수행되어야 들어갈 수 있다.
        - turn의 초기값이 i라고 하면, j가 먼저수행될 수는 없다. while(turn ≠ i);로 block이 되고 있는데, 초기값이 i이기 때문에 j는 i가 수행되기 전까지는 j가 절대 수행될 수 없음.

    - Bounded Waiting

        - 만약 Pi의 수행시간이 매우 짧고, Pj가 수행시간이 매우 길다면 Pi는 반드시 Pj의 수행을 기달려야만 한다. (반드시 alternate)
        - 또, 만약 Pj가 수행중일 때 dead lock이 발생해서 프로세스가 멈추게 되면, Pi는 절대 실행될 수 없다. → turn = i가 수행될 수 없기 때문이다.

        ⇒ turn 덕분에 Mutual Section이 가능해졌지만, Progress, Bounded Waiting이 해결 불가능

---

- Algorithm 2

```c
bool flag[2];
// initially flag[0] = flag[1] = false

do {
	flag[i] = true;
	while (flag[j]);
		// critical section
	flag[i] = false;
		// remainder section
} while (1);

// 하나만 들어가기 위해서, flag 도입.
```

- 이전의 알고리즘에서는 반드시 번갈아서만 갈 수 있기 때문에, 문제점이 발생했다. 하지만, 이번에는 이전에 문제가 됐던 turn 변수의 작용이 없기 때문에 번갈아서 동작하지 않아도 된다.

- 문제점

    - Pj가 Critical Section에서 잘못되면, flag[i] = false가 되지 못한다. 즉, Pi는 들어갈 수 없다. 이건 뭔가 잘못되었을 때만 발생하기 때문에 맞는 것이라고 볼 수도 있다.
    - 하지만, 어떠한 이유에 의해 Pi에서 flag[i] = true;가 되고, 그 순간 스케쥴링이 발생해서 Pj의 flag[j] = true; 가 된다면, 둘 다 while에서 block 돼서 들어갈 수 없게 된다.

---

- Peterson’s Solution : 교과서적인 설명으로는 다 가능하지만, 코딩을 해서 현실적으로 돌려보면 문제가 발생할 수 있다.

    - 현대 컴퓨터 아키텍처는 load나 store같은 machine-language instructions를 기준으로 동작되기 때문에, 피터슨 해결법이 올바르게 동작할 것이라는 보장은 할 수 없다. 
    - 피터슨 해결법은 두 개의 프로세스들이 critical section과 remainder section을 나눠서 수행하도록 제한하는 것이다.

    두 개의 프로세스가 있다. i = 0, j = 1이라고 생각해보자.

**Peterson’s Solution**

```c
while (1) {
	flag[i] = true;
	turn = j;
	// j의 차례이거나, j의 flag가 true,
	// 그러면 i의 실행을 막는다.
	while (flag[j] && turn == j);
		// critical section
	flag[i] = false;
		// remainder section
}
```

```c
while (1) {
	flag[j] = true;
	turn = i;
	// i의 차례이거나, i의 flag가 true,
	// 그러면 j의 실행을 막는다.
	while (flag[i] && turn == i);
		// critical section
	flag[j] = false;
		// remainder section
}
```

⇒ Entry Section은 O(1), 데이터가 하나임.

이 예제를 살펴봤을 때, 몇 가지 경우를 생각해볼 수 있다.

> turn은 절대 동시에 두 개의 값을 가질 수 없고,  
> flag는 상호 의존성 없이 수행할 수 있게 된다.  
> ⇒ 이를 결합해서 문제를 해결할 수 있다.

1. 두 개가 동시에 수행된다고 가정할 때.

    flag[i] == flag[j] == true가 된다. 이 때, turn = j, turn = i가 둘 다 실행될 것이지만, turn은 반드시 하나의 값만을 가지게 된다.

    예컨대, turn = j가 먼저 수행되었고, 그 다음 turn = i가 수행되었다. 그러면 현재 turn == i

    그렇게 되면, while (flag[i] && turn == i); 이 조건은 true가 되기 때문에, j 실행은 block된다.

    반대로, while (flag[j] && turn == j); 이 조건은 turn ≠ j이기 때문에, i는 실행된다.

    그러면서 계속 j의 실행은 막혀있고, i의 critical section이 모두 실행된 다음 flag[i] = false가 되면, while (flag[i] && turn == i); 에서 flag[i] == false가 되어서 j가 실행된다.

    만약, 두 개가 동시에 true가 되었다고 할 때, 두 코드가 순차적으로 진행된다고 해보자.

    먼저, i가 수행된다고 해보자.

    - i가 먼저 수행되면 turn = j가 수행되고, 그 다음에는 j가 수행돼서 turn = i가 된다.
    - 그러면 turn은 현재 i이기 때문에 i가 수행 중이라고 판단, i는 수행되고, j는 블록된다.

    그 다음으로는 j가 수행된다고 해보자.

    - j가 먼저 수행되면 turn = i가 수행되고, 그 다음에는 i가 수행돼서 turn = j가 된다.
    - 그러면 turn은 현재 j이기 때문에 j가 수행 중이라고 판단, j는 수행되고, i는 블록된다.

    다음으로는 한 쪽이 먼저 다 수행된다고 가정해보자.

    먼저, i가 수행된다고 해보자.

    - i가 먼저 수행되면 turn = j, 그 다음에는 while loop에 막히게 된다.
    - 현재 turn == j이고, flag[j] == true이므로 j가 수행 중이라고 판단(실제로는 수행 중은 아니지만) ⇒ 그러므로 i는 수행되지 않고 대기하게 된다.

    - 그 다음 j가 수행되면 turn = i가 된다.

        - 계속 j의 수행 ⇒ while loop의 조건에 막혀서 block되고, i가 수행된다.
            ⇒ flag[j] == true, turn == j
        - 바뀌자마자 i의 수행 ⇒ i가 turn == i가 되기 때문에 탈출, i가 수행된다.

    그 다음으로는 j가 수행된다고 해보자.

    - j가 먼저 수행되면 turn = i, 그 다음에는 while loop에 막히게 된다.
    - 현재 turn == i이고, flag[i] == true이므로, i가 수행 중이라고 판단(실제로는 수행 중은 아니지만) ⇒ 그러므로 j는 수행되지 않고 대기하게 된다.

    - 그 다음 i가 수행되면 turn = j가 된다.

        - 계속 i의 수행 ⇒ while loop의 조건에 막혀서 block되고, i가 수행된다.
            ⇒ flag[i] == true, turn == i
        - 바뀌자마자 j의 수행 ⇒ j가 turn == j가 되기 때문에 탈출, j가 수행된다.

2. i가 먼저 수행된다고 가정할 때.

    flag[i] = true이고, turn = j가 실행된다. 이 때, while (flag[j] && turn == j); 조건에 의해서 현재 flag[j]가 true인 경우와 false인 경우로 나눌 수 있다.

    - 만약 flag[j]가 true라면? ⇒ j가 수행 준비 중이거나 이미 수행 중.

        - 아직 turn = i가 수행되지 않았거나, critical section이 수행중인 것.

            - turn = i가 수행된다. ⇒ i가 실행된다. j는 현재 turn == i이고, i가 먼저 실행돼서 flag[i] == true이기 때문에 당연하게도 j의 실행은 block된다.
            - j의 critical section이 수행 중. ⇒ 그렇다면, j가 수행 중이지만, turn은 i로 바꿔버린 것이다. j의 실행이 끝나면 flag[j] = false가 돼서 i 실행.

    - 만약 flag[j]가 false라면? ⇒ j가 수행 중이 아니므로.

        - 바로 i가 실행된다.

3. j가 먼저 수행된다고 가정할 때.

flag[j] = true이고, turn = i가 실행된다. 이 때, while (flag[i] && turn == i); 조건에 의해서 현재 flag[i]가 true인 경우와 false인 경우로 나눌 수 있다.

- 만약 flag[i]가 true라면? ⇒ i가 수행 준비 중이거나 이미 수행 중.

    - 아직 turn = j가 수행되지 않았거나, critical section이 수행중인 것.

        - turn = j가 수행된다. ⇒ j가 실행된다. i는 현재 turn == j이고, j가 먼저 실행돼서 flag[j] == true이기 때문에 당연하게도 i의 실행은 block된다.
        - i의 critical section이 수행 중. ⇒ 그렇다면, i가 수행 중이지만, turn은 j로 바꿔버린 것이다. i의 수행이 끝나면 flag[i] = false가 돼서 j 실행.

- 만약 flag[i]가 false라면? ⇒ i가 수행 중이 아니므로.

    - 바로 j가 수행된다. 

⇒ 이를 종합적으로 판단했을 때, 두 개의 flag가 동시에 true가 되어도 turn 조건에 의해서 절대로 critical section이 동시에 수행될 수 없다. 혹은 한 번에 하나만 true가 되면, turn이 반대쪽 프로세스로 지정되기 때문에 다른쪽 프로세스가 수행되고 있다고 상정되어 while loop에 block되기 때문에 수행되지 못하고 기다리고 있는다. 이 경우, 반대쪽 프로세스는 실제로 critical section이 수행 중일 수도 있고, 수행이 끝나고 돌아오고 있을 수도 있다. 만약 critical section이 수행 중이었다면 실제로 block되는 것이 맞으므로 대기하다가 수행이 끝나면 자신도 수행을 하게 된다. 그게 아니었다면, 다시 두 개의 경우로 나뉘어지게 되는데, 반대쪽 프로세스가 자신의 flag를 true로 하는 작업을 수행했었다면 block되고 있다가 turn이 나의 것으로 바뀌는 순간 block이 해제되어 프로세스가 수행될 것이고, 만약 remainder section이 수행되고 있어서 반대쪽 프로세스의 flag가 false였다면 while loop에 block되지 않고 바로 내 프로세스가 수행된다.  
⇒ 이런 결과를 거쳐서 Peterson’s solution은 항상 critical section problem을 해결하고 수행될 수 있다.

---

- Bakery Algorithm

    - 은행에 있는 번호표를 생각해보자. 엄청 큰 은행인데, 번호표 발급기는 딱 하나만 있다. 사람이 너무 많아서, 발급기를 여러 개 두었는데 이 번호가 서로 중복되지 않도록 해결해야 한다.
    - Critical Section은 은행원을 만나는 것. 가장 작은 번호가 CS에 들어간다.
    - Process는 P(i), P(j)로 표현하고, i &lt; j이면 P(i)가 먼저 처리된다.
    - 넘버는 반드시 증가하는 형태로만 발급된다.

    (a, b) &lt; (c, d) if a &lt; c or if a = c and b &lt; d (두 개의 세트를 비교한다.)

    max (a0, …, a(n-1)) is a number, k, such that k ≥ a(i); for i = 0, …, n-1

    - Shared Data

        - boolean choosing[n];
        - int number[n];
        - 모두 false이다.

        ⇒ choosing은 모두 false, number는 모두 0.

```c
do {

	// 번호표 발급을 위해 기다림.
	choosing[i] = true;
	number[i] = max(number[0], number[i], ..., number[n-1])+1;
	// 전체가 갖는 값 중 최대값 + 1
	choosing[i] = false;
	
	for (j = 0; j < n; j++) {
		while(choosing[j]); // j(0~n)가 choosing을 하고 있다면 기다린다.
		// 내가 하나를 뽑고 왔는데, 만약 그게 4라면, 그 뒤에 뽑는 choosing[j] 프로세스들은
		// 아무리 뽑아도 4보다 작거나 같은 숫자는 나올 수 없다. 항상 5 이상으로 나옴.
		// 그래서 일단 다 기다려주는 것.

		while((number[j] != 0) && ((number[j], j) < (number[i], i)));
		// number[j] < number[i] 인지 본다. 내 기준은 i인데, 내 기준으로 나보다 작은 것이
		// 있는가? 를 본다. (우선권 파악), 만약 같은 것이 있다면 j와 i를 비교.
		// 그래서 j가 더 작으면 j가 우선, i가 더 작으면 i가 우선.
		// 둘다 비교해본다는 뜻. (Process ID인 i or j가 더 작은 쪽이 우선이다.)

		// 그리고, number[j] != 0을 체크한다. 이는 number[j]가 이미 처리된 번호라는 뜻.
		// 즉, 처리된 번호라면 비교를 안하고, 처리된 번호가 아니라면 내가 우선인지
		// 아니면 나보다 우선인 것이 있는지 체크한다는 뜻.
	}

		// critical section

	number[i] = 0;

		// remainder section

} while (1);
```

⇒ 교과서에서는 잘 된다고 표현된다.

## 문제점

- while loop blocking에서 문제가 발생할 수 있다.

    - for loop 내에서 O(n^2)의 알고리즘이 동작하는데, 너무 길고 복잡하다.
    - 그래서 이걸 운영체제에게 맡기려니까 너무 복잡하다. 그러므로 H/W로 해결책을 넘겨보자.
        ⇒ S/W 로직을 회로로 만들어서 구현하는 것이 좋다…
    - entry section이 너무 길어서, entry section은 그 자체로는 atomical 하지 않기 때문에 스케쥴링이 발생한다. 그래서 그들 사이에서 너무 긴 for loop 때문에 꼬일 수도 있다.
